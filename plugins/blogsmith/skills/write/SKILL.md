# 아티클 작성

`$ARGUMENTS`에서 글감 폴더 이름과 `--style`, `--platform`, `--workspace`를 뽑는다.

## 첫 번째 원칙: 문체가 SEO 를 이긴다

둘이 부딪히면 문체를 따른다. 근거가 둘이다.

네이버는 자동 생성 패턴이 감지된 문서를 검색결과에서 제외한다.
SEO 를 위해 문체를 깨면 노출 자체가 안 된다.

그리고 문체를 깨면 문체 문서를 만든 의미가 사라진다.

**부딪히지 않는 SEO 는 전부 적용한다.** 숫자 넣기, 사실 정보 정확히 쓰기,
단점 언급하기는 문체와 안 부딪힌다. 오히려 `natural-voice` 와 같은 방향이다.

## 두 번째 원칙: 소스에 없는 것을 쓰지 않는다

가격, 시간, 거리, 이름은 `notes.md` 에 있는 것만 쓴다.
없으면 비워두고 사용자에게 묻는다. 그럴듯하게 채우지 않는다.

경험도 마찬가지다. 사용자가 겪지 않은 것을 겪은 것처럼 쓰지 않는다.

## 1. 작업공간과 소스 찾기

```bash
${CLAUDE_SKILL_DIR}/../../scripts/find-workspace.sh "<--workspace 값, 없으면 생략>"
```

출력된 절대 경로가 기준이다. 소스는 `<작업공간>/sources/<글감 폴더>/` 다.

**스크립트가 1을 반환하면 중단한다.** 경로를 추측해 쓰지 않는다.
엉뚱한 폴더에 산출물이 생기고, 사용자는 어디에 생겼는지 모른다.

아래에 후보가 있으면 스크립트가 같이 낸다. 그때는 그 후보로 다시 돌릴지 묻는다.
**후보가 하나뿐이어도 묻는다.** 사용자가 지명하지 않은 곳에 산출물을 쓰면
엉뚱한 데 파일이 쌓인다. 묻는 값은 질문 한 번이고 틀렸을 때 값은 그것보다 크다.
후보가 없다고 나오면 `/blogsmith:init` 을 먼저 실행하라고 안내한다.

폴더 이름에 띄어쓰기가 들어갈 수 있다. **셸 명령에서 경로는 항상 따옴표로 감싼다.**

글감 폴더가 없으면 `sources/` 목록을 보여주고 무엇을 쓸지 묻는다.

### 산출물이 이미 있으면 여기서 묻는다

같은 글감을 다시 쓰는 것이라 **무엇을 하려는지 우리가 알 수 없다.**
플랫폼만 바꾸는 것일 수도, 문체를 고쳐 다시 쓰는 것일 수도, 품질을 재는 것일 수도 있다.

**초안은커녕 아웃라인을 잡기 전에 묻는다.** 나중에 물으면 버릴 것을 이미 만든 뒤다.

```
플랫폼이 같으면    덮어쓰기 / v 번호로 남기기 / 기존 것을 바탕으로 고치기
플랫폼이 다르면    나란히 두기 / 기존 것을 바탕으로 고치기 / 덮어쓰기
```

**`v` 번호는 시간 축이고 접미사는 플랫폼 축이다.**
나란히 둘 때는 넷 다 `article.naver.md` 처럼 양쪽 모두에 접미사를 붙인다.

보기 문구와 각 선택의 동작은 [rerun.md](rerun.md) 에 있다.

**묻지 않고 덮어쓰지 않는다.** `learn-style` 은 문체 문서가 있으면 덮어쓸지 확인한다.
같은 성격인데 한쪽에만 있었다.

## 2. 문체와 플랫폼 결정

**문체.** `--style` 이 없으면 `blog.config.json` 의 `defaultStyle` 을 쓴다.
그것도 없으면 `styles/` 를 본다.

**문체 문서가 하나뿐이면 묻지 않고 그것을 쓴다.** 고를 것이 없는데 묻는 것은 마찰이다.
둘 이상이면 목록을 보여주고 고르게 한다. 하나도 없으면 `learn-style` 을 먼저 돌리라고 안내한다.

**플랫폼.** 이 순서로 정한다.

```
1. --platform
2. blog.config.json 의 defaultPlatform
3. 문체 문서 frontmatter 의 platform
```

### 키가 없을 때 무엇으로 보는가

설정 파일에 키가 빠져 있을 수 있다. `init` 이후에 늘어난 키가 그렇다.
`update` 가 채워주지만 안 돌렸을 수도 있으므로 없을 때의 값을 정해둔다.

| 키 | 없으면 |
|---|---|
| `defaultStyle` | 위 규칙대로. 문체 문서가 하나면 그것, 둘 이상이면 묻는다 |
| `defaultPlatform` | 문체 문서 frontmatter 의 `platform` |
| `imageMode` | `filename` |

**없다고 멈추지 않는다.** 값을 정하고 무엇으로 봤는지 2단계 알림에 함께 적는다. 예시다.

```
문체 casual-review, 플랫폼 naver 로 씁니다.
imageMode 가 설정에 없어 filename 으로 봅니다. /blogsmith:update 로 채울 수 있습니다.
```

**옛 작업공간에 `author` 가 남아 있을 수 있다.** 형식 `1.2.0` 에서 뺀 키다.
읽지 않는다. 채워져 있어도 무시한다.

문체 문서의 `platform` 은 **어디서 배웠는지**이고 `--platform` 은 **어디에 쓸지**다.
보통 같지만 다를 수 있다. 다르면 문체 문서의 `플랫폼 종속 규칙` 에서
`그 외` 쪽 대체를 적용한다.

**묻지 말고 정한 뒤 알린다.** 매번 물으면 마찰이다. 예시다.

```
문체 casual-review, 플랫폼 naver 로 씁니다.
```

## 3. 지식 불러오기

플랫폼에 따라 참조할 것이 다르다.

| 플랫폼 | 참조 |
|---|---|
| `naver` | `naver-seo` |
| `tistory` `velog` `markdown` | `google-seo`, `geo-aeo` |

`natural-voice` 는 플랫폼과 무관하게 항상 참조한다.

## 4. 소스 읽기

`notes.md` 를 읽고 사진 파일 목록을 만든다.

**어느 사진을 열지는 `notes.md` 가 정한다.**

사진 메모에서 `[읽기]` 가 붙은 줄의 파일만 연다.

```
- 01_외관_간판작음.jpg
- 04_메뉴판.jpg [읽기]        ← 이 한 장만 연다
```

메뉴판 가격이나 간판 영업시간처럼 **파일명만으로는 알 수 없는 것**을 사용자가 고른 것이다.
표시가 없으면 열지 않는다. **빠뜨린 것 같아도 알리지 않는다.**
표시할 자리는 `sources/README.md` 가 안내하고 있고, 고르는 것은 사용자 몫이다.

`imageMode` 는 전체를 한꺼번에 정하는 스위치다.

| 값 | 동작 |
|---|---|
| `filename` (기본) | `[읽기]` 가 붙은 사진만 연다 |
| `read` | 표시와 무관하게 전부 연다 |
| `ask` | `[읽기]` 가 붙은 사진을 열기 전에 목록을 보여주고 확인받는다 |

**여는 것은 장당 토큰이 크다.** 열 장을 다 열면 본문보다 사진이 더 비싸다.
그래서 기본이 안 여는 쪽이고 필요한 것만 골라 붙이는 방식이다.

### 사진은 `photo-reader` 가 연다

**여는 사진이 하나라도 있으면 서브에이전트를 띄운다.** 직접 열지 않는다.

이미지는 한 번 대화에 들어오면 **그 뒤 모든 턴에서 다시 실린다.**
초안과 `audit.py` 3회와 검수까지 그 무게를 지고 간다. 필요한 것은 값이지 이미지가 아니다.

프롬프트에 넣을 것이다.

```
사진 절대 경로 목록      여는 것만. 위 표가 정한 집합이다
그 사진의 소스 메모       notes.md 에서 그 줄을 가져온다
소스의 관련 값           notes.md 에 적힌 가격이나 시간. 대조하라고 준다
```

**절대 경로로 준다.** 서브에이전트는 자기 작업 디렉토리를 따로 가진다.

**여는 사진이 여섯 장을 넘으면 절반씩 나눠 둘을 함께 띄운다.**
사진마다 독립이라 나눠도 값이 안 상하고 병렬로 돌아 빨라진다.
다섯 장 이하는 하나로 띄운다. 띄우는 값이 나누는 값보다 크다.

**HEIC 변환은 여기서 한다.** 아래 절이 정한 대로 확인하고 바꾼 뒤,
변환된 파일 경로를 에이전트에 넘긴다. `sips` 가 없으면 사용자에게 물어야 하는데
에이전트는 못 묻는다.

### HEIC 는 열기 전에 JPG 로 바꾼다

`Read` 도구가 `.heic` 를 이미지로 인식하지 못한다. 여는 사진만 바꾼다.

```bash
command -v sips && sips -s format jpeg "<원본>.HEIC" --out "<원본>.jpg"
```

**`sips` 는 macOS 에만 있다.** 없으면 바꾸려 들지 말고 알리고 묻는다.
변환본은 원본 옆에 두고 **원본은 지우지 않는다.**

문구와 안 될 때의 처리는 [photos.md](photos.md) 에 있다.

### 읽은 값은 쓰든 안 쓰든 남긴다

사진 안에서 읽어낸 값도 소스다. `notes.md` 와 맞춰보고 셋으로 갈라
`review.md` 의 `사진에서 읽은 값` 에 적는다.

```
1  일치              4  없던 값 중 쓴 것
2  어긋난 값          5  없던 값 중 안 쓴 것
3  사진으로 확인 못 한 것  6  못 읽은 자리
```

**4번과 5번만 이쪽 판단이다.** 본문을 써봐야 무엇을 넣고 뺐는지 알기 때문이다.
나머지 넷은 `photo-reader` 가 낸 것을 그대로 옮긴다.

**없으면 없다고 적는다.** 빈 갈래를 지우면 안 본 것인지 봐서 없는 것인지 구분이 안 된다.

갈래별 뜻과 예시는 [outputs.md](outputs.md) 에 있다.

**시킨 것과 겪은 것에 붙는 값은 쓴다.** 사용자가 `[읽기]` 를 붙인 이유가 그것이다.
메뉴판이면 시킨 메뉴의 가격이고 안내판이면 그날의 영업시간이다.
안 시킨 메뉴까지 나열하지는 않는다. 겪지 않은 것이고 나열은 문체를 무너뜨린다.

**안 쓴 값을 말없이 버리지 않는다.** 사용자는 그 사진을 골라 표시했는데
안에 무슨 값이 있었는지도 모른 채 끝난다. 적어두면 넣을지 사용자가 정한다.

## 5. 분량 판단

문체 문서의 관찰 범위와 소스를 견준다. 사진 장수와 메모 분량을 본다.

**소스가 관찰 범위 상단을 크게 넘으면 분할을 제안한다.** 임의로 나누지 않는다.

나누기로 하면 문체 문서의 연재 규칙을 따른다.
제목에 번호를 달고, 이어지는 편은 앞 편을 참조하고, 앞 편 끝에 다음 편을 예고한다.

### 하한에 못 미치면 관찰끼리 부딪힌다

사진이 관찰 하한보다 적으면 어느 관찰을 맞출지가 갈린다.
사진 9장에 묶음 관찰이 `편당 7~16개` 이고 크기 관찰이 `1장이 71%` 인 경우가 그랬다.

```
1장씩 아홉 묶음      묶음 9개로 맞지만 1장 비율이 100% 가 된다
크게 묶어 다섯 묶음   비율은 맞지만 묶음 수가 하한에 못 미친다
```

**비율을 먼저 맞추고 묶음 수를 역산한다.** 사진 수는 재료가 정하고 비율은 습관이다.
9장이면 1장 다섯 묶음과 2장 두 묶음으로 일곱 묶음이 되고 1장 비율이 71%다. 둘 다 맞는다.

**억지로 맞추지 않는다.** 어느 조합으로도 두 관찰이 동시에 안 맞으면 비율을 따르고
묶음 수가 하한에 못 미친 것을 `review.md` 의 `못 지킨 것` 에 적는다.
그때는 사진을 더 갖고 있는지 사용자에게 알린다.

**분량도 같다.** 메모가 얇아 관찰 하한에 못 미치면 채우려고 늘리지 않는다.
`google-seo` 가 명시적으로 경고하는 자리이고 `두 번째 원칙` 과도 부딪힌다.
짧게 쓰고 무엇이 모자랐는지 적는다.

**문체 관찰 자체가 SEO 권장을 크게 넘으면 한 번 알린다.**
분량은 문체가 아니라 사용자가 SEO 를 몰라 굳어진 습관일 수 있다.

```
이 문체는 편당 사진 8~21장, 문단 24~70개입니다.
네이버 권장은 본문 800~2,000자인데 이 문체는 그보다 깁니다.

AI 브리핑이 전체 쿼리의 20%를 처리하는 지금은
한 편이 한 주제를 다루는 쪽이 인용에 유리합니다.

이번 소스는 두 편으로 나눌 만합니다. 나눌까요?
```

한 번만 알린다. 매번 띄우면 잔소리가 된다.

## 6. 제목과 아웃라인 확인

**초안을 쓰기 전에 반드시 확인받는다.** 아웃라인은 짧아서 보여주는 비용이 작은데,
틀린 채로 초안까지 가면 전부 버려야 한다. 예시다.

```
제목 후보
  1. 성수동 코너스톤, 2층 창가가 정답이다
  2. 웨이팅 20분 감수할 만한 성수동 카페
  3. 성수동 코너스톤 후기 (주차 안 됨 주의)

아웃라인
  도입     주말 웨이팅 20분, 그늘 없어 힘들었음
  1        2층 창가 자리가 제일 낫다        [사진 02]
  2        콜드브루는 산미가 강한 편         [사진 03]
  3        작업하러 가기엔 애매하다
  마무리    재방문 의사, 평일 추천

넣을 사실  가격 3종, 영업시간, 주차 불가, 콘센트 위치, 도보 7분
안 넣은 것  (소스에 있는데 뺀 것이 있으면 여기 표시)
```

제목을 함께 보여준다. 사용자가 가장 관여하고 싶어 하는 부분이다.

## 7. 초안 작성

문체 문서의 `재현 규칙` 을 따른다.

**관찰 항목이 재현 규칙과 달라 보여도 규칙을 따른다.**
관찰은 학습 당시의 기록이고 규칙은 사용자가 정한 결정이다.
`캡션은 55묶음 중 7개(13%)` 는 지금까지 어땠는지이고,
`사진 묶음마다 캡션을 단다` 는 앞으로 어떻게 쓰겠다는 선택이다.
사용자가 관찰과 다르게 정할 수 있고 그것이 정상이다.
`learn-style` 이 판단 필요 항목을 물어보는 이유가 그것이다.

관찰을 근거로 규칙을 어기지 않는다. 이것을 규칙 충돌로 보지 않는다.

**1~10번은 필수다.** 하나라도 깨면 그 사람 글이 아니다.
11~20번은 여유가 있을 때 챙긴다. 충돌하면 번호가 작은 쪽을 따른다.

`하지 말 것` 을 어기지 않는다. 여기가 문체를 가르는 선이다.

`플랫폼 종속 규칙` 은 대상 플랫폼에 맞는 쪽을 적용한다.

**네이버 전용 컴포넌트에 걸린 규칙 둘은 대체가 정해져 있다.**

| 규칙 | 네이버 | 그 외 |
|---|---|---|
| 지도 카드로 위치를 준다 | 지도 카드 | 인용 블록에 상호, 주소, 지도 링크 |
| 사진에 캡션을 단다 | `se-caption` | `![캡션](파일)` 의 alt |

지도는 인용 블록으로 옮겨도 의도가 남는다. 본문과 갈리고 주소가 보인다.
기호를 앞에 붙일지는 `하지 말 것` 을 보고 정한다. 이모지 0회인 문체에 `📍` 를 붙이면 어긋난다.

**캡션은 절반만 재현된다.** `alt` 는 이미지가 정상으로 뜨면 화면에 안 보인다.
그래도 채운다. `google-seo` 가 요구하고 이미지가 안 뜰 때와 화면 낭독기에서 쓰인다.

**alt 에 넣었다고 캡션 규칙을 지킨 것으로 세지 않는다.**
보이는 캡션이 재현되지 않았다는 것을 `못 지킨 것` 에 적는다.

```
[캡션] 사진 묶음마다 캡션을 단다 (규칙 19)
   alt 에는 넣었지만 마크다운 계열에는 보이는 캡션 문법이 없습니다.
   에디터에서 사진을 올린 뒤 캡션란에 같은 문구를 넣어주세요.
```

`근거 발췌` 는 읽지 않는다. 남의 문장이다.

**컴포넌트가 아니라 역할대로 마크다운을 쓴다.**

문체 문서는 `대제목은 인용 컴포넌트` 처럼 네이버 컴포넌트 이름으로 말한다.
그것은 에디터에서 무엇을 누를지의 안내지 `article.md` 의 표기가 아니다.

| 역할 | 표기 |
|---|---|
| 글 제목 | `#` |
| 대제목 | `##` |
| 소제목 | `###` |
| 진짜 인용 | `>` |
| 구분선 | `---` |
| 굵게 | `**` |

**대제목을 인용 블록으로 쓰는 문체라도 `##` 로 적는다.**
`>` 로 적으면 셋이 어긋난다. 의미상 제목인데 인용문이라고 표시하는 것이고,
티스토리와 velog 에서 제목이 인용문 상자로 렌더되고,
네이버에서는 어차피 기호가 텍스트로 남아 사용자가 지워야 하므로 얻는 것이 없다.

어느 컴포넌트로 만들지는 `meta.md` 의 발행 전 확인에 적어 사용자에게 넘긴다.

**문단 안 줄바꿈은 플랫폼이 표기를 정한다.**

문체 문서가 한 문장을 절 경계에서 자르라고 하거나 빈 줄로 덩어리를 나누라고 하면
그 줄바꿈이 산출물에 살아 있어야 한다. 그런데 표기가 플랫폼마다 다르다.

| 플랫폼 | 문단 안 줄바꿈 |
|---|---|
| `naver` | 개행 그대로. 아무것도 붙이지 않는다 |
| `tistory` `velog` `markdown` | 줄 끝에 공백 두 칸 |

네이버는 PC 웹 스마트에디터 ONE 과 모바일 앱 둘 다 붙여넣기에서 개행을 줄바꿈으로 살린다.
확인하고 정했다. 그래서 공백을 넣지 않는다. 넣으면 본문에 딸려 들어갈 수 있다.

마크다운은 개행 하나를 줄바꿈으로 보지 않는다. 공백 두 칸이 없으면 앞 줄에 이어 붙는다.
**백슬래시는 쓰지 않는다.** 한글 폰트에서 원화 기호로 렌더되어 본문에 그대로 남는다.

문단과 문단 사이는 플랫폼과 무관하게 빈 줄이다. 문단 안의 빈 줄도 빈 줄로 낸다.

**사진은 마크다운 문법으로 자리를 표시한다.**

```markdown
![간판이 작아서 지나치기 쉽다](01_외관_간판작음.jpg)
```

네이버에 붙여넣으면 이 줄이 그대로 남는데, 어디에 무엇을 넣을지 보여서 오히려 낫다.
사진을 올리고 그 줄을 지우면 된다.

## 8. 검사

`audit.py` 를 돌린다.

```bash
python3 "${CLAUDE_SKILL_DIR}/../natural-voice/scripts/audit.py" "<작업공간>/output/<글감>/article.md"
```

검토 항목이 나오면 고치고 다시 돌린다. **최대 3회다.**

3회를 넘으면 대개 규칙끼리 충돌하는 상황이고 기계가 못 푼다.
남은 항목을 `review.md` 에 적고 **왜 못 고쳤는지**를 함께 쓴다.
규칙 충돌인지, 소스가 없어서인지, 판단이 필요한지 구분돼야 한다.

**고칠 수 없는 것만 남았으면 3회를 채우지 않는다.**
남은 것이 오탐이거나 소스에 없는 값을 요구하는 것이면 더 돌려도 결과가 같다.
그 상태에서 횟수를 채우려 들면 **없는 숫자를 지어내게 된다.**
두 번째 원칙을 어기는 자리다. 멈추고 `review.md` 에 적는다.

한 번 돌리고 남은 것을 하나씩 갈라 본다.

| 남은 것 | 어떻게 |
|---|---|
| 오탐 | 고치지 않는다. 한글 고유명사가 든 단위가 자주 걸린다 |
| 소스에 값이 없다 | 고치지 않는다. `소스에 없어서 비워둔 것` 에 적어 사용자에게 넘긴다 |
| 소스에 값이 있다 | 고친다. 이때만 다시 돌린다 |

셋째가 하나도 없으면 다시 돌릴 이유가 없다.

**`audit.py` 와 문체 문서가 충돌하면 문체 문서를 따른다.**
`audit.py` 는 일반 규칙이고 문체 문서는 그 사람 개별 규칙이다.
이 경우 `audit.py` 결과는 경고로만 적는다.

### 스크립트로 안 되는 것은 에이전트가 판단한다

`audit.py` 를 돌리는 것으로 검사가 끝나지 않는다.
`natural-voice` 의 `에이전트가 읽고 판단할 것` 여섯 항목을 거치고
**답을 `review.md` 에 적는다.** 사용자는 그 답을 읽고 확인한다.

- 소리 내어 읽어 입에 안 붙는 곳이 있는가
- 형용사를 지워도 뜻이 남는가. 남으면 근거로 바꿨는가
- 첫 문단에 숫자나 고유명사가 있는가
- 필자의 견해와 단점이 있는가
- 문단마다 요약 문장이 붙어 있지 않은가
- 경험 서술이 소스에 근거하는가

통과라고만 적지 않는다. **무엇을 보고 그렇게 판단했는지 한 줄씩 쓴다.**
답을 적어야 실제로 보게 되고, 사용자가 `review.md` 만 열어도 검사 범위를 안다.

세 번째 항목이 특히 자주 샌다.
`예전에 이슈였던 게 생각나서 찾아갔다` 처럼 무엇을 가리키는지 안 밝힌 도입이
`audit.py` 의 구체성 검사를 통과한다. 짧은 덩어리는 검사 대상에서 빠지기 때문이다.

## 9. 산출물

`<작업공간>/output/<글감 폴더>/` 에 넷을 만든다. 폴더 이름은 소스와 같게 한다.

```
article.md    본문
photos.md     사진 순서, 위치, 캡션
meta.md       제목 후보, 태그, 메타 디스크립션, 발행 전 확인
review.md     audit 결과, 검색 노출 체크, 못 지킨 것
```

**`--platform naver` 면 `naver.html` 을 하나 더 만든다.**
스마트에디터 ONE 이 붙여넣기에서 인용구·구분선·목록·표·링크·굵게를 살린다.
`article.md` 를 텍스트로 붙이면 그 자리에 마크다운 기호가 글자로 남아
사용자가 하나씩 지우고 다시 만들어야 한다.

**`article.md` 에서 만드는 파생물이다. 손으로 고치지 않는다.**
`article.md` 가 정본이고 둘이 어긋나면 낡은 쪽을 붙여넣게 된다.

형식은 [outputs.md](outputs.md) 에 있다.
이미 있는 산출물을 어떻게 할지는 1단계에서 이미 물었다.

**`review.md` 의 절은 `outputs.md` 가 정한 것만 쓴다.** 절을 임의로 더하지 않는다.
실행마다 구성이 달라지면 두 판을 나란히 놓고 무엇이 달라졌는지 볼 수가 없다.

**태그는 30개까지 뽑는다.** 사용자가 그중에서 골라 쓴다.
