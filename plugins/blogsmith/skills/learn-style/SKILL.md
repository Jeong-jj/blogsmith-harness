# 문체 학습

`$ARGUMENTS`에서 URL 목록과 `--name`, `--workspace` 값을 뽑는다.

## 작업공간 찾기

먼저 작업공간을 정한다. `blog.config.json`이 있는 디렉토리다.

```bash
${CLAUDE_SKILL_DIR}/../../scripts/find-workspace.sh "<--workspace 값, 없으면 생략>"
```

`--workspace`를 주면 그 경로를 쓰고, 없으면 현재 디렉토리부터 위로 거슬러 찾는다.
git이 `.git`을 찾는 방식과 같다. 사용자가 `sources/` 안에서 실행해도 찾아낸다.

**출력된 절대 경로를 이후 모든 경로의 기준으로 삼는다.**
`styles/<이름>.md`는 `<작업공간>/styles/<이름>.md`를 뜻한다.

**스크립트가 1을 반환하면 중단한다.** 경로를 추측해 쓰지 않는다.
사유가 표준 오류로 나오니 그대로 전달한다.

아래에 후보가 있으면 스크립트가 같이 낸다. 그때는 그 후보로 다시 돌릴지 묻는다.
**후보가 하나뿐이어도 묻는다.** 사용자가 지명하지 않은 곳에 산출물을 쓰면
엉뚱한 데 파일이 쌓인다. 묻는 값은 질문 한 번이고 틀렸을 때 값은 그것보다 크다.
후보가 없다고 나오면 `/blogsmith:init` 을 먼저 실행하라고 안내한다.

## 경로 처리

사용자 폴더 이름에 띄어쓰기가 들어갈 수 있다. `2026-08-03 성수동 카페` 같은 식이다.

**셸 명령에서 경로는 항상 따옴표로 감싼다.** 감싸지 않으면 띄어쓰기에서 인자가 쪼개져
엉뚱한 경로를 만들거나 실패한다. 괄호와 앰퍼샌드도 같은 문제를 일으킨다.

```bash
ls "<작업공간>/styles"
```

## 입력 확인

**URL 개수.** 개별 글 주소를 받는다. 블로그 메인 주소가 아니다.
`_raw/<이름>/` 이 이미 있으면 그 안의 항목 수도 편수에 더해 센다.

- 5편을 권장한다. 한 편만 보면 그 글의 특성인지 그 사람의 습관인지 구분되지 않는다.
- 3편 미만이면 표본이 부족하다고 알리고, 계속할지 물은 뒤 진행한다.
- 6편을 넘으면 앞의 6편만 쓴다. 더 읽어도 정확도가 눈에 띄게 오르지 않는다.

**플랫폼.** URL 의 도메인을 보고 플랫폼을 판별한다. 문체 문서의 `platform` 에 기록한다.

**여러 플랫폼이 섞여 있으면 확인한다.** 같은 사람이라도 플랫폼이 다르면 문체가 갈린다.
한 문서에 섞으면 두 목소리의 평균이 나와서 둘 다 아닌 문체가 된다.

```
URL 5개 중 네이버 3편, velog 2편이 섞여 있습니다.

플랫폼이 다르면 같은 사람이라도 문체가 갈립니다.
한 문서에 섞으면 둘 다 아닌 문체가 나옵니다.

→ 네이버 3편만 / velog 2편만 / 그래도 섞기
```

섞기를 고르면 `플랫폼 종속 규칙`을 플랫폼별로 나눠 적는다.
같은 사람이 두 곳에 크로스포스팅하는 경우가 있으므로 막지는 않는다.

**이름.** `--name`이 없으면 사용자에게 묻는다. 파일명이 되므로 영문 소문자와 하이픈으로 받는다.
`<작업공간>/styles/<이름>.md`가 이미 있으면 덮어쓸지 확인한다.

## 분석

`style-analyst` 서브에이전트를 **하나** 띄운다. URL마다 나누지 않는다.
한 에이전트가 전부 읽어야 편들을 맞대어 비교할 수 있고, 그 비교가 이 작업의 핵심이다.

프롬프트에 넣을 것:

- URL 목록 전부
- **본문 수집 스크립트의 절대 경로**
  `${CLAUDE_SKILL_DIR}/scripts/fetch-post.py`
  에이전트는 경로 치환을 받지 못하므로 우리가 풀어서 넘겨야 한다
- `<작업공간>/styles/_raw/<이름>/`이 있으면 그 안의 경로도 함께.
  **바로 아래 항목 하나가 글 하나다.** 파일이면 그 파일, 폴더면 그 안의 캡처 전부가 한 편이다.
  세는 법과 예외 처리는 [raw.md](raw.md)에 있다
- 저장 경로. **절대 경로로 준다.** `<작업공간>/styles/<이름>.md`
  서브에이전트는 자기 작업 디렉토리를 따로 가지므로 상대 경로를 주면 엉뚱한 곳에 쓴다
- `schema.md`의 내용 (`${CLAUDE_SKILL_DIR}/schema.md`를 읽어서 그대로 전달)

에이전트가 파일을 직접 쓰고 요약만 돌려준다.
글 5편의 본문이 이 대화로 들어오지 않게 하려는 구조다.

## 결과 확인

에이전트가 끝나면 파일을 읽어 일곱 가지를 검사한다.
일곱째는 `_raw/` 를 쓴 실행에서만 본다.

**1. 재현 규칙이 지시문인가.** "친근하게 쓴다" 같은 형용사 나열이면 재작성을 요청한다.
`schema.md`의 좋음과 나쁨 예시가 판단 기준이다.

**2. 규칙마다 예시가 붙었는가.** 예시가 없으면 무슨 말인지 모르는 규칙이 섞인다.

**3. 수치가 관찰 범위를 벗어나지 않는가.** 관찰이 `2~17%`인데 규칙이 `20%`면 제약이 아니다.
평균을 상한으로 쓴 곳도 찾는다. 그러면 편차가 사라진다.

**4. 규칙이 재료의 개수에 기대고 있지 않은가.** 여기가 제일 자주 샌다.
`한 편에 사진 8~20장`, `한 편에 한 번 4~6장`, `10장이 넘으면`처럼
사용자가 그날 가진 재료의 수를 조건으로 삼은 규칙을 찾는다.
사진이 아홉 장뿐인 날 그 규칙은 지킬 방법이 없다.
`같은 대상을 찍은 사진이면`, `한 끼에서 다음 끼로 넘어가면`, `같은 자리에서 찍은 것이면`처럼
성질 조건으로 바꾸게 한다. 무엇을 기준으로 묶는지는 블로그마다 다르므로
소스가 쓰는 기준을 그대로 쓰게 한다.

**5. 규칙의 조건이 관찰 항목과 같은 기준을 쓰는가.** 4번의 뒷면이다.
성질 조건으로 바뀌긴 했는데 그 성질이 소스의 것이 아니라 예로 든 어휘일 수 있다.

`사진` 항목이 `소제목 하나가 여러 장소를 묶은 자리` 라고 적었는데
규칙이 `같은 대상을 찍은 사진만 넣는다` 로 시작하면 둘이 다른 기준이다.
관찰은 소제목으로 묶는다고 하는데 규칙은 대상으로 묶는다고 한다.

관찰 항목의 기준과 규칙의 조건을 맞대어 읽는다.
어긋난 것이 규칙 안에 남아 있으면 앞뒤 문장이 충돌하는 형태로 드러난다.

```
한 묶음에는 같은 대상을 찍은 사진만 넣는다. 대상이 바뀌면 글로 끊는다.
소제목 하나가 여러 장소를 묶고 있으면 그 장소들을 한 묶음에 넣는다.
```

여러 장소는 대상이 여럿인데 한 묶음에 넣으라고 한다.
앞 문장이 덧씌운 것이고 뒤 문장이 진짜 기준이다. 관찰 쪽 기준으로 다시 쓰게 한다.

충돌은 증상 하나지 검사 방법이 아니다. 꼬리 없이 한 줄로 끝난 규칙은
덧씌워도 매끄러워서 충돌이 안 보인다. 그때는 관찰과 직접 대조한다.

**6. 하지 말 것이 비어 있지 않은가.** 여기가 비면 문체가 뭉개진다.
무엇을 쓰는지만큼 무엇을 안 쓰는지가 그 사람을 만든다.

**7. `_raw/` 를 썼으면 그 편의 범위를 밝혔는가.** 이 검사만 조건부다.

붙여넣은 본문에는 사진과 구분선이 없을 수 있고, 캡처가 글 끝까지 안 닿았으면 그 뒤가 없다.
**그런데 문서에는 못 본 것과 없는 것이 똑같이 안 보인다.**

```
출처 표기    로컬 절대경로가 남아 있지 않은가. `_raw` 를 지우면 가리킬 곳이 사라진다
분모        구조 관찰의 편수가 셀 수 있었던 편수인가. 3편 중 2편에서만 셌으면 그렇게 적혔는가
0회         `하지 말 것` 의 0회가 끝까지 본 편에서 나온 값인가
```

세 번째가 제일 나쁘게 샌다. 캡처가 글 끝을 못 담은 실행에서 `지도 카드를 붙이지 않는다` 가
`하지 말 것` 에 들어간 적이 있다. 그 편은 글 끝에 장소 카드로 주소를 주고 있었다.
**못 본 것이 금지가 됐다.**

## 판단이 갈린 항목 확인

**여기가 이 스킬에서 가장 중요한 절차다.**

표본이 5편이라 한두 편에서만 나타난 특징은 습관인지 우연인지 구분되지 않는다.
그런데 **사용자는 자기 블로그를 알기 때문에 안다.** 물어보면 대부분 바로 풀린다.

에이전트가 보고한 `판단 필요` 목록을 하나씩 확인한다. 한 번에 다 묻지 말고 순서대로 제시한다.

**`AskUserQuestion` 을 쓴다. 텍스트로 나열하지 않는다.**
이 도구가 한 화면에 한 항목씩 보기와 함께 내밀고 앞뒤로 넘길 수 있게 해준다.
목록을 통째로 늘어놓으면 집중이 흩어져 답이 뭉개진다.

이 도구는 **한 번에 4개까지** 받는다. 항목이 더 많으면 나눠서 여러 번 부른다.
10개면 4, 4, 2다. 사용자 쪽에서는 이어서 넘어가므로 끊긴 티가 나지 않는다.

보기를 만드는 법이다.

- 보기는 **2~4개**. `기타`는 자동으로 붙으므로 직접 넣지 않는다
- 기본은 `규칙으로` `조건부` `안 씀` 셋이다
- **조건부는 조건까지 보기 안에 써넣는다.** 관찰에서 읽어낸 조건을 제시하고
  고르기만 하면 되게 한다. `조건부(어떤 조건인지)`처럼 되물으면 도구를 쓰는 의미가 없다
- 보기 설명에 **그 선택이 문서에 어떻게 들어가는지** 적는다.
  `규칙으로` 만으로는 문장이 어떻게 바뀔지 모른다
- 질문에 근거를 붙인다. 몇 편에서 몇 회, 나머지 편은 어땠는지, 실제 문장 하나

```
질문   그림 이모지를 규칙으로 넣을까요? 5편 중 3편, 총 6개입니다 (🐰 🥲 🙄 ⭐⭐).
       문장 맨 끝에 하나만 붙이고 연속으로 쓰지 않습니다. post2와 post3은 0개입니다.

보기1  규칙으로 (편당 0~3개)
       "문장 끝에 이모지를 하나만 붙인다. 한 편에 0~3개, 연속으로 붙이지 않는다."

보기2  조건부 (감정이 실릴 때만)
       아쉬움이나 황당함처럼 감정이 실리는 대목에서만 붙이고 정보 문단에는 안 붙입니다.

보기3  안 씀
       하지 말 것으로 보냅니다. 자음(ㅎㅋㅠ)과 텍스트 이모티콘으로만 처리합니다.
```

답을 받으면 문서를 고친다.

- **규칙으로**: `재현 규칙`에 넣는다. 예시도 함께
- **조건부**: 조건을 명시해 `재현 규칙`에 넣는다
- **플랫폼 기능**: `플랫폼 종속 규칙`으로 보낸다
- **안 씀**: `하지 말 것`에 넣는다
- **모르겠다**: 그때만 관찰로 남긴다

**규칙이 20개를 넘으면 새 번호를 만들지 말고 기존 규칙에 조건으로 붙인다.**
소제목 번호는 소제목 규칙에, 별점은 마무리 규칙에, 이모지는 자음 웃음 규칙에 들어간다.
성격이 같은 자리를 찾으면 대개 들어갈 곳이 있다.

**에디터 기능에 따라 동작이 갈리면 `플랫폼 종속 규칙` 이다.**
본문 상단 해시태그는 네이버에서 실제 태그로 걸리고 다른 곳에서는 텍스트로만 남는다.
`재현 규칙` 에 두면 velog 에서 죽은 문자열이 붙는다.

**빈칸을 남긴 채 끝내지 않는다.** 문체 문서는 여기서 완성된다.
나중에 `write`가 돌 때 "이건 판단이 안 됐습니다"라고 하면 그때는 늦다.

### 고치는 것도 에이전트가 한다

**답을 다 받으면 `style-analyst` 를 새로 띄워 반영시킨다. 메인이 직접 고치지 않는다.**

분석을 맡았던 에이전트는 요약을 돌려주고 이미 끝났다. 이어붙일 수 없다.
그렇다고 메인이 문서를 열어 고치면 **글 본문이 이 대화로 들어온다.**
`분석` 절이 서브에이전트를 쓰는 이유가 정확히 그것을 막으려는 것이라 여기서 무너진다.

새 에이전트에 넘길 것이다.

- 문체 문서 경로. **절대 경로로 준다**
- 소스 경로 전부. URL 목록과 `_raw/<이름>/`. 다시 세어야 하는 답이 있다
- 항목마다 사용자가 고른 답과 그 답이 들어갈 자리
- `결과 확인` 에서 걸린 것도 함께. 한 번에 고치는 편이 왕복이 적다
- `schema.md` 경로

**걸린 것을 따로 고치지 않는다.** 검사에서 나온 지적과 사용자 답이 같은 규칙을 건드릴 때가 있다.
따로 두 번 고치면 뒤에 고친 쪽이 앞을 덮는다.

## 보고

- 저장 경로
- 읽은 글 수와 실패한 URL
- 문체 세 줄 요약
- 판단 필요 항목과 그 처리 결과

기본 문체로 지정할지 묻는다. 원하면 `<작업공간>/blog.config.json`의 `defaultStyle`에 이름을 넣는다.

## 정리

`<작업공간>/styles/_raw/<이름>/`을 썼다면 분석이 끝난 뒤 지울지 묻는다.

원문 복제본이 남아 있을 이유가 없다. 문체 문서에 규칙이 들어갔으면 역할이 끝났다.
다만 사용자가 자기 글을 넣은 경우라면 남겨둬도 상관없으니 강제로 지우지 않는다.

## 실패 처리

`fetch-post.py`는 blogsmith 라고 신분을 밝히고 요청한다.
플랫폼별 방침은 [domains.md](domains.md)에 정리해 뒀다.

**거절당하면 우회하지 않는다.** `User-Agent`를 바꿔가며 재시도하지 않는다.
비공개 글과 삭제된 글도 마찬가지로 실패로 처리한다.

스크립트가 실패로 내는 것은 넷이다. 사유가 표준 오류로 나오니 그대로 전달한다.

```
받지 못했습니다      curl 이 실패했거나 응답이 너무 짧다
HTTP 404 입니다      상태 코드가 200 이 아니다
글 페이지가 아닙니다   200 인데 글이 아니다
잠긴 글입니다        200 이고 글 페이지인데 비밀번호가 걸려 있다
```

**막히는 방식이 플랫폼마다 다르다.** 열한 경우로 확인했다.

| | 응답 | 잡는 것 |
|---|---|---|
| 네이버 비공개 | 200, 안내 페이지 | `og:type` |
| 네이버 없는 글 | 404 | 상태 코드 |
| velog 비공개 | 404 또는 200 | 상태 코드 또는 `og:type` |
| 티스토리 비공개 | 403 | 상태 코드 |
| 티스토리 보호글 | 200, `og:type=article` | 비밀번호 입력칸 |
| 블로그 메인 주소 | 200, `og:type=website` | `og:type` |

`og:type` 이 `article` 인지로 대부분 갈린다. 셋 다 글 페이지에만 이 값을 준다.

**보호글은 그것으로 안 갈린다.** 글 페이지 껍데기에 비밀번호 화면만 얹혀 오기 때문이다.
본문 자리에 비밀번호 입력칸이 있는지로 따로 본다.
로그인을 OAuth 로 넘기는 세 플랫폼에서는 글 페이지에 그 칸이 없다.

**멀쩡한 글이 실패로 나올 수 있다.** 스킨이 `og:type` 을 안 넣거나
비밀번호 입력칸을 사이드바에 두면 그렇다. 그때는 아래 `_raw/` 로 본문을 직접 넣는다.
없는 글을 학습하는 것보다 못 읽고 멈추는 쪽이 낫다.

3편 미만만 읽혔으면 문서를 만들지 않는다. 표본이 부족한 채로 만든 문체 문서는
틀린 규칙을 확신 있게 적어놓기 때문에 없느니만 못하다.

이때 실패한 주소를 사유와 함께 보여주고 아래 셋을 제안한다.

```
1. 글을 캡처해 이미지로 저장 후 재실행
   <작업공간>/styles/_raw/<이름>/01/ 안에 위에서 아래 순서로
   글 끝까지 찍는다. 마지막 구분선과 태그 목록이 보이면 끝이다

2. 본문을 복사해 저장 후 재실행
   같은 위치에 01.txt
   자기 글일 때 쓴다. 남의 글은 대개 복사가 막혀 있다
   사진과 구분선이 안 담기는 경우가 많다. 그러면 구조 관찰이 빈다

3. 실패한 주소를 빼고 나머지로 진행
   남은 편수가 3편 미만이면 다른 글을 더 받는다
```

**캡처를 먼저 권한다.** 토큰은 복사가 싸지만 복사에는 사진과 구분선이 잘 안 담긴다.
잃는 양과 그것이 판단까지 틀어지게 하는 경로는 [raw.md](raw.md)에 재둔 값이 있다.

넣는 자리, 캡처를 읽는 법, 범위가 모자란지 보는 법도 [raw.md](raw.md)에 있다.
