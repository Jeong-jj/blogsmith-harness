# 본문을 직접 넣는 법

자동 수집이 막혔을 때 쓰는 경로다. `fetch-post.py` 가 실패로 낸 글을 사용자가 채운다.

## 무엇을 고르나

**캡처가 기본이다.**

`learn-style` 의 주 용도는 남의 블로그 문체 학습인데 **남의 글은 복사가 대개 막힌다.**
네이버 앱에서는 본문을 선택할 수 없고, PC 웹도 블로거가 복사 방지를 켜면 막힌다.
자기 글이면 관리자 화면에서 원문을 꺼낼 수 있으므로 그때만 복사가 실질 선택지다.

| | 복사 | 캡처 |
|---|---|---|
| 남의 글 | 대개 불가 | 가능 |
| 자기 글 | 가능 | 가능 |
| 토큰 | 적다 | 장당 크다 |
| 남는 정보 | 글자만 | 화면에 보이는 전부 |

**토큰이 싸다고 복사를 먼저 권하지 않는다.** 복사는 사진과 구분선을 통째로 잃는다.
아래 `복사가 잃는 것` 을 보면 그 값이 나온다.

## 넣는 법

**`_raw/<이름>/` 바로 아래 항목 하나가 글 하나다.**

```
styles/_raw/houself/
  01.txt          첫 번째 글. 본문을 복사해 넣은 경우
  02/             두 번째 글. 캡처가 여러 장이라 폴더로 묶는다
    01.png
    02.png
    03.png
  03/             세 번째 글
    01.png
```

파일이든 폴더든 **바로 아래 항목 수가 곧 편수다.** 열어보지 않고 센다.
폴더 안의 번호는 위에서 아래로 이어지는 캡처 순서다.

**바로 아래에 이미지가 둘 이상 평평하게 있으면 묻는다.** 한 편을 나눠 찍은 것인지
여러 편을 한 장씩 찍은 것인지 파일만 봐서는 안 갈린다.

```
바로 아래에 이미지 파일이 둘 이상 평평하게 있습니다.

  01.png ~ 10.png

한 편을 나눠 찍은 것이면 폴더로 묶어주세요. 여러 편이면 그대로 진행합니다.

→ 한 편이다 (폴더로 묶어 다시 실행) / 여러 편이다 (그대로 진행)
```

이미지가 하나뿐이면 묻지 않는다. 한 편인 것이 확실하다.

## 캡처를 찍는 법

사용자에게 안내할 내용이다.

- **글 끝까지 찍는다.** 마지막 구분선과 그 아래 태그 목록이 보이면 끝이다
- **장 사이를 조금씩 겹친다.** 문단이 잘리면 그 자리의 줄바꿈 관찰이 깨진다
- 화면 폭을 바꾸지 않는다. 폭이 달라지면 한 줄에 들어가는 글자 수가 달라진다

## 캡처를 읽을 때

**화면에는 글이 아닌 것이 같이 들어온다.** 세 종류다.

```
앱 UI      상단 시간·배터리, 블로그 이름, 하단 좋아요·댓글·공유·탭바
           매 장에 반복되므로 장수만큼 중복된다
광고        관심 있을 만한 상품 같은 블록. 상품 이미지를 본문 사진으로 세면 안 된다
잘린 문장    장 경계에서 문장이 반씩 걸린다. 겹쳐 찍었으면 같은 문장이 두 장에 나온다
```

**세지 않는다.** 앱 UI 와 광고는 본문이 아니고, 겹친 문장은 한 번만 센다.

이것은 `fetch-post.py` 가 HTML 에서 겪은 것과 같은 종류다.
공감 UI 와 CCL 고지가 본문으로 섞여 사진 수가 세 배로 부풀었던 적이 있다.
캡처에는 그것을 막는 코드가 없으므로 읽는 쪽이 가른다.

## 범위가 모자란지 본다

마지막 캡처 한 장만 보면 판정된다.

```
1. 아래쪽이 본문 문장 중간에서 끊긴다
2. 글 끝에 오는 것이 안 보인다. 마지막 구분선, 태그 목록, 공감·댓글 영역
```

**마무리 문장이 없다는 것은 신호로 쓰지 않는다.** 마무리 습관을 지금 학습하는 중이라
순환이 된다. 원래 툭 끊는 문체일 수도 있다.

걸리면 한 번 묻는다.

```
캡처가 글 끝까지 안 닿은 것 같습니다.

  10.png  본문 문장 중간에서 끝납니다
          마지막 구분선과 태그 목록이 안 보입니다

→ 뒤를 더 찍어 넣고 다시 실행 / 이대로 진행
```

**이대로 진행하면 문체 문서에 범위를 적는다.**

```
- 글 대비 비율: ... (3편 중 1편은 캡처 범위까지만 관찰)
```

`0회` 라고 적으려면 끝까지 봤어야 한다. 범위를 안 적으면 못 본 것이 없는 것이 된다.

## 복사가 잃는 것

2026-08-27 에 같은 글 하나를 세 방식으로 읽어 쟀다.

```
              URL(기준)   캡처       복사
사진           47장        46장       33장
사진 묶음       36개        34개       23개
그 글의 몫      14장 13묶음  13장 11묶음  0
```

캡처의 오차는 방식의 손실이 아니라 **끝까지 안 찍은 범위 부족**이었다.
복사는 그 글의 사진과 구분선이 통째로 0이 된다.

**복사가 아니면 안 나오는 규칙이 있다.**

```
사진 묶음 하나에 텍스트 덩어리 하나
묶음 경계는 그 묶음을 받는 텍스트가 이름 붙인 범위와 같다
정확한 표가 필요하면 숫자를 옮기지 말고 공식 화면을 캡처해 붙인다
```

셋 다 사진 자리를 봐야 나온다.

**그리고 판단까지 틀어질 수 있다.** 같은 항목을 두 실행이 똑같이 물었는데 답이 갈렸다.

```
캡처   그 편은 같은 두 줄 구조인데 접두가 없습니다        → 조건부
복사   로컬에 붙여넣은 1편만 번호도 | 도 없습니다        → 항상
```

복사본에는 접두가 원래 없었는지 복사에서 날아갔는지 표시가 없다.
사용자가 손실로 읽고 `항상` 을 골라서 규칙이 그 편을 위반하게 됐다.

**그래서 복사를 쓸 때는 무엇을 못 보는지 먼저 알린다.**

## 출처 표기

`근거 발췌` 의 출처는 로컬 절대경로로 적지 않는다. `_raw` 를 지우면 가리킬 곳이 사라진다.

```
좋음   > 출처: 캡처 (배내골 편) 01.png
좋음   > 출처: 붙여넣기 (배내골 편) 01.txt
나쁨   > 출처: /Users/.../workspace/styles/_raw/test6/01.txt
```

어느 글인지 알아볼 수 있게 짧게 적는다.
